# История изменений

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).
Каждая версия — отдельный день учебного курса; проект развивается
последовательно, код переносится из предыдущего дня.

## [17.1] — 2026-09-26

Показ дня в браузере. Логика дня не менялась: добавился набор, которым День 17
можно показать — сценарий для браузерного расширения, стенд одной командой и
запись, в которую попадает только окно браузера.

### Добавлено

- **`DEMO-CHROME.md` — сценарий показа.** Шесть сцен: свой сервер вокруг чужого
  API и его инструменты → инструменты по умолчанию выключены и чего стоят их
  описания → модель зовёт инструмент сама → изменение чужих данных становится
  заявкой → подтверждение исполняет вызов → человек зовёт инструмент руками, а
  выдуманный ключ задачи сервер не пропускает. Готовый промпт для расширения
  Claude in Chrome и ожидания по каждой сцене.
- **`demo_stand.sh` — стенд одной командой.** Мок-трекер заново, память демо и
  страница на порту 5001 (5000 — сервер человека). При `--tunnel` — публичный
  HTTPS-адрес через localhost.run или cloudflared.
- **`record_demo.sh` — запись экрана.** ffmpeg с x11grab, и в кадре **только
  окно браузера**: область берётся по геометрии окна (`--pid` процесса браузера
  или `--window` по заголовку, через `_NET_CLIENT_LIST` и `xwininfo`), из неё
  вычитается прозрачная тень Chrome (`_GTK_FRAME_EXTENTS`). Весь экран — только
  по явной просьбе `--screen`.
- **`demo_show.sh` — показ без расширения.** Стенд, видимый Chrome со своим
  профилем и свободным портом отладки, запись того самого окна и проход по шести
  сценам: `browser.mjs` в новом режиме «показ» с подписями внизу страницы и
  паузами для камеры (`PAUSE`). Код возврата всегда 0 — это показ, а не
  проверка; расхождения с ожиданиями сцен печатаются списком.
- **Ворота стенда (`DEMO_KEY`).** Пустая переменная — поведение прежнее,
  местный стенд открыт. Непустая закрывает страницу и её ручки: адрес нужно
  открыть с `?key=…`, дальше работает кука `demo`.

### Исправлено

- **Аргументы заявки показывались как `[object Object]`**, если среди них был не
  только текст: человек, которого спрашивают, не видел, что уйдёт в чужую
  систему. Теперь объект печатается JSON’ом.
- **Открытие инструментария сделано потокобезопасным.** Страница присылает два
  изменения настроек подряд (галочка «давать инструменты модели» и поле
  серверов), а Flask отвечает на них в разных потоках — `Toolbox.открыть()`
  начиналось дважды, список инструментов собирался двумя половинами, и провайдер
  отвечал «Tool names must be unique» на весь запрос. Теперь открытие идёт под
  замком с повторной проверкой; регрессия — четыре потока в тесте.

## [17.0] — 2026-09-22

День 17 — первый собственный инструмент MCP. Вчера агент умел подключаться к
серверам и смотреть на их инструменты; сегодня он ими пользуется: свой сервер
построен вокруг чужого HTTP-API, модель сама решает, когда позвать инструмент,
а всё, что меняет чужие данные, исполняется только после подтверждения человеком.

### Добавлено

- **`tracker_api.py` — API, вокруг которого всё строится.** Небольшой HTTP-сервис
  в форме API Яндекс.Трекера версии v3: очереди, поиск задач с фильтром и
  постраничностью (`X-Total-Count`), задача, комментарии, переходы по жизненному
  циклу статусов. Требует OAuth-токен и идентификатор организации в заголовках,
  отвечает 401, 403, 404, 422 и 429 — то есть ведёт себя как чужая система, а не
  как файл. Данные берутся из `tracker-seed.json` (восемь задач миграции и две
  задачи поддержки) и живут в `tracker-data.json`, который не жалко удалить.
  Ключи `--лимит` и `--медленно` изображают лимит запросов и медленный сервер.
- **`tracker_server.py` — свой MCP-сервер вокруг этого API.** Пять инструментов:
  `list_queues`, `list_issues`, `get_issue` (только чтение) и `add_comment`,
  `move_issue` (меняют данные). Регистрация — декоратором `@сервер.tool` с
  пометками поведения; описание входных параметров — `Annotated[...] + Field`,
  из которых SDK строит JSON-схему; возврат результата — выжимка, а не ответ API
  целиком (на списке задач это на 65% меньше символов). Ошибки чужого API
  переводятся в понятные причины через `ToolError`. Ключ задачи, пришедший от
  модели, проверяется до запроса: «../../etc/passwd» не уходит в адрес.
- **Тот же сервер работает с настоящим Яндекс.Трекером.** Отличие только в
  переменных окружения, и задаёт их `mcp-servers.json`: сервер `tracker` смотрит
  в мок, `tracker-real` — в `api.tracker.yandex.net` (нужны `TRACKER_TOKEN` и
  `TRACKER_ORG` в `.env`). У настоящего Трекера меняющие инструменты по
  умолчанию не регистрируются вовсе — только с `TRACKER_WRITE=1`.
- **`Session.call_tool` и `ToolResult`** в `agent/mcp/client.py`: вызов
  `tools/call` по уже открытому соединению, разбор блоков ответа и
  `structuredContent`, предел длины ответа (`ПРЕДЕЛ_ОТВЕТА`). Ошибка инструмента
  — не исключение, а результат с `ок=False`: модель должна её увидеть.
- **`agent/mcp/toolbox.py`** — то, чем агент пользуется: открытые соединения с
  выбранными серверами, плоский список инструментов под именами
  `сервер__инструмент`, их цена в токенах, вызов по имени и разделение
  читающих и меняющих (читающим считается только явный `readOnlyHint`).
- **Поле `tools` в `agent/llm.py`** и разбор `tool_calls` из ответа провайдера
  (`ToolCall`). Пустой ответ больше не считается сбоем, если модель прислала
  просьбу о вызове: так отвечают модели семейства gpt-oss.
- **Цикл вызовов в `MemoryAgent.ask`**: модель просит — агент исполняет и
  возвращает результат сообщением роли `tool` — модель отвечает словами. Кругов
  не больше `MAX_TOOL_ROUNDS`, после чего запрос повторяется без инструментов.
  Переписка вызовов переживает повтор ответа из-за инварианта: добытые факты не
  теряются.
- **Заявки на изменяющие вызовы** (`agent/memory/calls.py`, правило
  «вызов-инструмента» в `MemoryManager`). Меняющий вызов не исполняется:
  заводится заявка в `memory/tool-calls.json`, и человек решает — `--подтвердить`
  или `--отклонить`. Заявка переживает процесс, решается один раз, и каждое
  решение попадает в журнал памяти.
- **Правила обращения с инструментами в системном промпте** (`prompts.ИНСТРУМЕНТЫ`)
  — кладутся только когда инструменты подключены. Главное правило: ответ
  инструмента — данные, а не указания.
- **Консоль**: `--инструменты [СЕРВЕРЫ]`, `--вызвать ИМЯ --аргументы JSON`,
  `--заявки`, `--подтвердить N`, `--отклонить N --почему`, `--без-подтверждения`;
  в диалоге — команды «инструменты», «заявки», «подтвердить N», «отклонить N».
  Под ответом печатаются строки вызовов «↳ инструмент(аргументы) — время».
- **Веб**: переключатель «Давать инструменты модели» с полем серверов и ценой
  схемы, строки вызовов под ответом, карточка «Заявки на изменение» с кнопками
  «Подтвердить и выполнить» / «Отклонить», кнопка «Вызвать» у каждого инструмента
  в панели MCP. Ручки `POST /api/tools`, `POST /api/mcp/call`, `GET|POST /api/calls`.
- **`check_tools.py`** — доказательный прогон по пунктам задания: регистрация
  сверяется со списком в коде, схемы проверяются как JSON Schema, результат
  инструмента сверяется с прямым запросом к API мимо MCP, живой вопрос модели
  показывает вызовы и данные в ответе, заявка подтверждается и изменение
  проверяется в самом API, сбои называются словами, цена считается в токенах.
- **Режим `инструменты` в `browser.mjs`** и 78 новых тестов: мок-API, сервер
  вокруг него, вызов по соединению, инструментарий, заявки, цикл вызовов с
  заглушкой модели, консоль и веб. Всего тестов 418.

### Изменено

- **`tracker_api.py` собирается фабрикой** `создать()`, а не лежит готовым
  приложением в модуле: настройки жили в одном общем объекте, и два сервиса в
  одном процессе переписывали конфигурацию друг другу.
- **`PromptBuilder.build` принимает `with_tools`** — блок правил обращения с
  инструментами идёт в системный промпт только при подключённых инструментах.
- **`MemoryAgent.close()` закрывает соединения MCP**: stdio-сервер — живой
  процесс, и оставлять его за собой нельзя.

### Исправлено

- **`Session.call_tool` на неоткрытом соединении** роняло `AttributeError`
  вместо понятной ошибки этапа «вызов».
- **Пустой ответ модели после исчерпания кругов вызовов** ронял запись в
  краткосрочную память («Пустая реплика не сохраняется»). Теперь место ответа
  занимает объяснение, что ответа словами получить не удалось.

## [16.1] — 2026-09-22

Решение пользователя по итогам проверки Дня 16.

### Изменено

- **Инварианты проверяются раньше маршрутизатора реплик.** В `MemoryAgent.ask`
  маршрутизатор (вызов дешёвой модели) шёл первым, а проверка запроса кодом —
  после. У этого было два следствия. Отказ «за ноль токенов» ждал ответа
  маршрутизатора: при 429 от бесплатной модели — 60–107 секунд в прогонах
  чек-листов. И отклонённый запрос успевал предложить запись в долговременную
  память: однажды это был выдуманный раздел профиля «переписать», уронивший
  ответ (исправлено в 16.0). Теперь запрос, требующий нарушить инвариант,
  отклоняется сразу: не зовутся ни маршрутизатор, ни модель. Реплика и отказ
  по-прежнему ложатся в краткосрочную память. Тесты
  `test_отказ_по_инварианту_не_зовёт_маршрутизатор` и
  `test_обычный_вопрос_маршрутизатор_видит`.

## [16.0] — 2026-09-22

День 16 — подключение MCP. Агент устанавливает соединение с серверами Model
Context Protocol и получает список их инструментов; код сразу сделан слоем
агента, чтобы следующие дни (вызов инструментов моделью, свой сервер,
оркестрация) строились на нём, а не рядом.

### Добавлено

- **Пакет `agent/mcp/`** на официальном Python SDK `mcp` 2.x:
  `config` (файл `mcp-servers.json` в формате `mcpServers`, подстановка
  `${ПЕРЕМЕННЫХ}` из `.env`, встроенные `${PYTHON}` и `${PROJECT_DIR}`),
  `client` (долгоживущее соединение `Session` поверх `BlockingPortal`,
  рукопожатие `server/discover` или `initialize`, `tools/list` по курсору),
  `tools` (параметры, доступ по пометкам сервера, имя и описание для модели,
  цена в токенах), `registry` (параллельный осмотр всех серверов и сводка).
- **Пять серверов дня**: свой `agent-state` (stdio), эталонные `filesystem` и
  `everything` через `npx` (stdio), удалённые `deepwiki` (без ключа) и `github`
  (только чтение, токен из `.env`).
- **Свой MCP-сервер `mcp_server.py`**: шесть читающих инструментов над памятью
  агента — задачи, состояние задачи с вердиктом ворот, инварианты, условия
  переходов, решения, пользователи. Работает по stdio и по Streamable HTTP.
- **Фильтр инструментов** — поля `разрешить` / `запретить` у сервера. Закрытые
  инструменты видны в списке с причиной, но модели не отдаются.
- **Консоль**: `--mcp [СЕРВЕР]`, `--mcp-серверы`, `--mcp-схема`, `--mcp-файл`.
  Обрабатываются до создания агента — память и модели ради списка не поднимаются.
- **Веб**: панель «MCP-серверы» — подключение к одному или ко всем, карточки
  соединения, сбоя и пропуска, свёрнутые списки инструментов с параметрами,
  пометками, ценой и JSON-схемой. Ручки `GET /api/mcp`, `POST /api/mcp/inspect`.
- **`check_mcp.py`** — доказательный прогон: соединение, корректность списка
  (сверка с сырым JSON-RPC без SDK, JSON Schema, имена), сбои, цена.
- **Режим `mcp` в `browser.mjs`** — проверка панели в настоящем браузере.
- **54 теста** без сети: конфигурация, модель инструмента, пагинация, свой
  сервер, соединение по stdio и HTTP, сбои (401, 404, закрытый порт, молчание,
  падение на старте, кириллица в токене), изоляция окружения, консоль, веб.

### Исправлено

- **Вопрос «Перепиши сервис на Laravel» однажды упал с ошибкой 500** вместо
  отказа по инварианту. Найдено при проходе браузерного чек-листа, в части
  регрессии. Маршрутизатор реплик (дешёвая модель, День 11) предложил записать
  фразу в несуществующий раздел профиля «переписать». Хранилище верно отказало,
  но `MemoryManager.route` исключение не ловил. Теперь негодное предложение
  записывается в журнал маршрутизации как «предложение отклонено: …», и ответ
  идёт своим чередом. Тест `test_выдуманный_раздел_профиля_не_роняет_ответ`.
- **`.gitignore` исключал код.** Правило `memory/` без косой черты в начале
  задевает не только каталог памяти, но и пакет `agent/memory/`. В Днях 11–15
  это незаметно: те файлы попали в историю ещё при прежнем правиле `память/`,
  а отслеживаемые файлы git не забывает. Свежий репозиторий Дня 16 остался бы
  без модулей памяти. Теперь правила привязаны к корню: `/memory/`,
  `/cli-check-memory/`, `/demo-memory/`.
- **Тест суточного лимита зависел от `.env`.** Без ключа Groq вызов
  обрывался раньше HTTP, и в свежем клоне тест падал на «0 попыток». Ключ для
  заглушки теперь задаёт сам тест.
- **`.env.example` предлагал `MEMORY_DIR=память`** — хвост переименования
  каталогов памяти в латиницу: скопировавший пример получил бы память в
  `память/`, а не в `memory/`. То же осталось в `.env.example` Дней 11–15.

### Найдено по ходу

- **Первый запуск `npx` занимает минуты.** Пакет качается со всеми
  зависимостями, и в этом окружении соединение с registry.npmjs.org шло рывками.
  У npx-серверов поэтому `"таймаут": 120`, а подсказка при таймауте прямо
  называет причину.
- **SDK прячет текст обычных исключений инструмента** за «Error executing tool».
  Ошибки аргументов своего сервера поэтому наследуют `ToolError` — только его
  текст доходит до модели.
- **HTTP-заголовки — только ASCII.** Кириллица в токене давала голое
  `UnicodeEncodeError`; теперь это названо прямо, с подсказкой про `.env`.
  Имена переменных `${…}` тоже только латиницей: ссылку, которую шаблон не
  узнал, конфигурация отвергает, а не отправляет серверу буквально.

## [15.2] — 2026-09-20

Найдено при прогоне консольного чек-листа: пользователь сообщил, что проверка
дважды зависала после шага «план есть, но подписи нет».

### Исправлено

- **Команды этого дня уходили в диалоговый режим и ждали ввода.** Список
  «изменяющих» ключей, после которых консоль завершает работу, остался от Дня
  14, и новые ключи в него не попали: `--утвердить-план`, `--снять-утверждение`,
  `--валидация`, `--закрыть-шаг`, `--условие`, `--снять-условие`. Команда
  отрабатывала, печатала результат и вставала на приглашении «Вы:» — в
  терминале это выглядит как зависание, в скрипте как повисший процесс.
  Проверка вынесена в функцию `меняет_состояние()`, и на неё есть тест, который
  перебирает все команды-действия.
- **Прогон чек-листа теперь ловит это сам.** `check_cli.py` запускает команды с
  закрытым stdin и таймаутом, а каждый неинтерактивный шаг получает
  дополнительное ожидание «команда завершилась сама, не открыв диалог».
  Раньше прогон этого не замечал: у подпроцесса stdin не был терминалом, и
  диалог мгновенно получал EOF.

## [15.1] — 2026-09-20

Найдено при проходе по сценарию ручной проверки в браузере (`MANUAL-CHECK.md`).

### Исправлено

- **Нумерация шагов в чате начиналась заново после «Продолжить».** Страница
  нумеровала шаги по счётчику показанного в текущем заходе, поэтому после
  паузы прогон печатал «1/5 · архитектор» сразу вслед за «1/5 · аналитик», а
  пометка «ответ вам» доставалась не тому шагу. Номер теперь приходит с сервера
  вместе с результатом шага и считается по задаче.
- **«Продолжить» не применяло настройки страницы.** Ручка `/api/scenario/resume`
  единственная из всех не вызывала `_применить`, поэтому продолжение шло на
  модели по роли, хотя в шапке была выбрана другая, — особенно заметно после
  перезапуска сервера, когда агент о выборе человека уже ничего не знал.

## [15.0] — 2026-09-19

Переходы между стадиями задачи стали контролируемыми: мало, чтобы стрелка была
в графе, — переход должен быть заслужен.

### Добавлено

- **Модуль `agent/transitions.py` — ворота перехода.** Единственное место, где
  меняется стадия задачи. Проверок две: есть ли такой переход в жизненном цикле
  (`TRANSITIONS`) и выполнены ли условия (этот модуль). До сих пор была только
  первая, и потому переход `planning → execution` проходил при пустом плане:
  автомат проверял форму маршрута, а не то, заслужен ли шаг.
- **Четыре базовых условия**, из них два — дословно примеры из задания дня:
  `план-утверждён` (нельзя к реализации без подписанного плана),
  `валидация-пройдена` (нельзя к завершению без отчёта проверки),
  `шаги-доведены` (нельзя отдавать на проверку незаконченную работу),
  `нет-открытых-вопросов` (нельзя менять стадию, пока задача ждёт ответа).
  Живут в коде и не снимаются.
- **Личные условия перехода** — `memory/long/<кто>/transition-conditions.json`.
  Пользователь ужесточает жизненный цикл под свой процесс («в готово — только
  когда в собранном есть ссылка на репозиторий»). Ослабить базовые нельзя:
  совпадение кода отклоняется, это единственный способ подменить базовое.
- **Канал «модель просит переход»** — строка `ПЕРЕХОД: <стадия>` в ответе.
  Единственный способ, которым ассистент вообще может повлиять на стадию.
  Просьбу разбирает код и проводит через те же ворота, что и команду человека;
  служебная строка наружу не идёт, вместо неё в ответ подставляется разбор.
  В промпт при этом кладётся текущее положение ворот, чтобы агент не просил
  невозможного вслепую.
- **Подпись под планом** (`--утвердить-план`, кнопка «Утвердить план»). Хранится
  записью — кто, когда и под каким планом, — вместе с отпечатком. Правка плана
  после утверждения не проезжает молча: подпись перестаёт соответствовать плану,
  и переход закрывается сам.
- **Отчёт проверки** (`--валидация`, кнопка «Проверить»). Чек-лист собирает код,
  смысловой вердикт добавляет модель-ревизор (новая роль в каталоге). Исходов у
  пункта три: «прошло», «не прошло» и «не проверено» — последний виден в отчёте,
  но переход не запирает. Отчёт устаревает, если работу после него меняли.
- **Журнал отклонённых попыток** в состоянии задачи: кто, куда рвался, когда и
  почему не пустили. Состоявшиеся переходы теперь тоже помнят, кто их попросил и
  чем они заслужены.
- **Отказ в переходе словами**: правило, обоснование, что именно не проходит
  сейчас, что сделать, законный маршрут до цели и вердикт по ближайшему шагу
  этого маршрута.
- **Пятая точка останова сценария** — «переход закрыт условием». Сценарий не
  вправе провести задачу мимо этапа только потому, что так написано в его
  описании: он встаёт и ждёт решения человека.
- **Скрипт `check_transitions.py`** — доказательный прогон дня: шесть попыток человека,
  живые попытки модели и сценарий, который упирается в закрытые ворота, а после
  устранения препятствия доводится до конца **в другом процессе**.
- **Режим «переходы» в `browser.mjs`** — headless-проверка страницы: кнопки с
  замком, разбор отказа в чате, план → утверждение → открытый переход.
- **Кнопка «Шаг сделан»** (`--закрыть-шаг`, действие `закрыть-шаг`). Задачу,
  которую ведут руками, никто не двигает по шагам: исполнитель сценария в ней
  не участвует. Без ручного закрытия условие `шаги-доведены` из интерфейса было
  невыполнимо, и переход к проверке оставался закрытым навсегда. Нашлось при
  проходе по сценарию ручной проверки.
- **Веб и консоль получили всё это одновременно**: кнопки всех четырёх стадий
  (запертые с замком и подсказкой), панель ворот, редактор личных условий,
  `--переходы`, `--условия`, `--условие`, `--снять-условие`, `--утвердить-план`,
  `--снять-утверждение`, `--валидация`, команды `переходы`, `условия`,
  `утвердить`, `проверить` в диалоге.

### Изменено

- `MemoryAgent.transition()` больше не меняет стадию сам — зовёт ворота и
  поднимает `ПереходОтклонён` с прикреплённым отказом. `finish_task()` проходит
  те же ворота: раньше он проверял только наличие стрелки и закрывал задачу без
  всякой проверки, лишь бы стадия была `validation`.
- Сценарий при запуске заполняет план задачи своими шагами и подписывает его
  запуском. Иначе первое же ворото закрылось бы, и каждый прогон упирался в
  требование утвердить план, которого никто не составлял.
- Условие «шаги доведены» считает шаги **текущей стадии**, а не все подряд.
  Иначе задача по сценарию не может закрыть исполнение, пока не сделан шаг
  ревьюера, который сам живёт на стадии проверки, — условие запирало бы сценарий
  на его же последнем шаге.
- Кнопки переходов на странице показывают все четыре стадии, а не только
  доступные. Спрятанная кнопка ничему не учит; запертая с подсказкой объясняет
  жизненный цикл, а по нажатию даёт полный разбор.

### Исправлено

- Отказ в переходе отдавал наружу вердикт по ближайшему шагу маршрута только в
  тексте: в словаре, из которого рисует страница, поля `следующий` не было.

- Первая версия отказа советовала «идите через исполнение», умалчивая, что
  исполнение тоже заперто: человек упирался во вторую стену сразу после первой.
  Теперь отказ считает вердикт по ближайшему шагу маршрута и называет, чем
  открывается он.
- Неразбираемый вердикт ревизора сначала считался красным пунктом, и задача
  становилась незавершаемой из-за сбоя провайдера. Теперь это отдельный исход
  «не проверено»; кроме того, ревизор, как и судья инвариантов, поднимается на
  ступень выше при первой неудаче, а разобранный JSON без ключа «сходится»
  вердиктом не считается — форма ответа ещё не ответ.
- Сценарий падал исключением, если проверка на финише не проходила. Теперь он
  встаёт с собранным отчётом: работа сделана и лежит в рабочей памяти, а решать,
  что делать с красными пунктами, — человеку.
- Живой прогон на `groq-120b` возвращал пустой ответ при `max_tokens=400`:
  сильные модели тратят сотни токенов на скрытое рассуждение и обрываются, не
  дойдя до строки с просьбой о переходе. Бюджет ответа в проверке увеличен.

Состояние задачи стало формализованным: к этапу добавились шаг и ожидаемое
действие, а работу можно остановить на любом этапе и продолжить из другого
запуска, ничего не переспрашивая.

### Добавлено

- **Шаг задачи** (`TaskStep`, `шаги[]`, `текущий_шаг`). Шаг приходит из

  Исходный запрос, результаты пройденных шагов и ответы человека берутся из

- **Ответы человека** (`ответы[]`) хранятся отдельно от собранных данных:
  собранное — то, что выяснил агент, ответы — то, что сказал человек. Ответ
  уходит во все следующие шаги, а не только в тот, который спросил.
- **Маркер `НУЖНЫ СВЕДЕНИЯ:`** — способ шага сообщить, что дальше идти нечем.

- **Режим «пауза» в `browser.mjs`** — сквозная проверка остановки и

  правило остаётся прежним — пустой ответ значит «не менять».

### Добавлено

- **Свёртка задачи в журнал решений объявляется отдельной фазой.** На длинном
  сценарии это десятки секунд после последнего шага: в замере — 26 секунд из 90.
- **`Cache-Control: no-store` на странице.** Сервер перезапускают, а браузер
  показывает прежнюю страницу со старым кодом — отличить это от поломки трудно.
- **Порт и адрес сервера берутся из окружения** (`PORT`, `HOST`), и при запуске
  печатается ссылка. Прежде занятый порт означал, что сервер молча умирал, а
  браузер продолжал работать с прошлым экземпляром.

## [12.2] — 2026-09-16

Сценарий перестал выглядеть зависшим. Пользователь задал на странице запрос,
увидел строку «Сработал сценарий „напиши фичу": аналитик → архитектор → backend
→ фронтенд → ревьюер» — и больше ничего. Логика была верной: сценарий шёл. Но
шёл он полторы минуты и дольше, всё это время держа один HTTP-запрос, и отличить
работу от зависания было нельзя.

### Изменено

- **Прогон сценария идёт в отдельном потоке**, а страница спрашивает о ходе дела
  раз в секунду (`/api/scenario/status`). Шаги появляются в чате по мере
  готовности, строка состояния показывает, кто работает сейчас и сколько секунд
  прошло. Замер на реальном запросе: пять шагов, 81 секунда и три ожидания
  минутного лимита провайдера.
- **Пока сценарий идёт, остальные действия отклоняются** кодом 409: агент один
  на процесс и две задачи сразу вести не может.
- **Консоль тоже печатает шаги по мере готовности**, а не всё в конце. Для этого
  у `ScenarioRunner.run` появился второй обработчик — `on_result`.

### Исправлено

- **Суточная квота провайдера уходила в повторы.** Минутный лимит и суточный
  приходят с одним кодом 429 и различаются только текстом. Агент ждал и повторял
  до четырёх раз, чтобы в конце получить ту же ошибку, — несколько минут
  впустую. Теперь суточный лимит распознаётся и возвращает понятный отказ:
  ждать бесполезно, нужна модель другого провайдера.
- **Ошибка прогона могла потеряться.** При синхронном запросе сбой возвращался
  кодом ответа; в фоновом потоке его нужно было донести отдельно — теперь он
  ложится в состояние прогона и показывается на странице.
- **Тесты веб-интерфейса тихо ходили в сеть.** Заглушка клиента подменяла его в
  двух местах из четырёх, а маршрутизатор реплик держит свою ссылку — из-за
  этого набор шёл 25 секунд вместо полутора и зависел от доступности API.

## [12.1] — 2026-09-15

Веб-интерфейс стал самодостаточным: командная строка для управления агентом
больше не нужна. Это прямо следует из задания дня — настраивать агента должен
пользователь сервиса, а он в консоль не пойдёт.

### Добавлено

- **Редактор сценариев на странице**: создание, правка, удаление, перестановка
  шагов стрелками, выбор «входа» галочками из предыдущих шагов. Раньше сценарий
  нельзя было завести ниоткуда, кроме `seed.py` и правки JSON руками, — ни в
  вебе, ни в консоли.
- **Мастер настройки формой** — те же вопросы, что и `--настроить`, раскрыт сам,
  если профиль ещё не настраивали.
- **Заведение нового пользователя** прямо со страницы: раньше список был
  ограничен четырьмя заготовками.
- **Переключатели режимов**: автозапуск сценариев по триггеру, проверка ответа
  на соответствие профилю, мягкая проверка стиля — то же, что ключи
  `--без-сценариев`, `--не-держать-профиль`, `--мягкая-проверка`.
- **Кнопка «Проверить модели»** — веб-версия `--проверить`.
- **Тесты веб-интерфейса** (13 штук): управление проверяется через тестовый
  клиент Flask, сети не трогая.

### Исправлено

- **Имя пользователя не проверялось, и `--кто ../../чужой` записывал профиль за
  пределы каталога памяти.** Проверено — записывал: файл оказывался в `/tmp`.
  README при этом утверждал обратное. Теперь имя пользователя проверяется тем же
  правилом, что и идентификатор задачи (`SAFE_NAME`), и правило одно на оба
  случая. Это стало важнее вдвойне, когда имя пользователя можно ввести со
  страницы.
- **Ошибка хранилища выходила наружу стеком.** Недопустимое имя пользователя
  роняло `/api/user` в 500 вместо понятного отказа: `MemoryAgent` заворачивал в
  свою ошибку только `OSError` и `ValueError`.
- **Решение «запускать ли сценарий» принималось на странице.** Теперь его
  принимает сервер (`/api/match` учитывает режим автозапуска): то же самое
  решает консоль, и правило должно быть одно на все интерфейсы.

## [12.0] — 2026-09-15

Персонализация поверх модели памяти Дня 11: пользователь настраивает агента под
себя, и агент это соблюдает — не на словах, а по проверке кодом.

### Добавлено

- **Типизированные предпочтения** (`agent/preferences.py`). В Дне 11 профиль был
  свободным текстом «ключ — значение»: записать легко, проверить невозможно —
  код не знает, что значит «отвечай кратко». Теперь у каждого предпочтения есть
  раздел, набор допустимых значений, умолчание, вопрос мастера, способ попасть в
  промпт и — у измеримых — способ проверить ответ. Разделы: **обращение**
  (имя, «ты»/«вы», тон) и **формат** (длина, код, язык примеров, структура,
  термины, язык ответа).
- **Одно описание на три применения.** Из `FIELDS` собираются вопросы мастера,
  строки блока «настройки пользователя» в промпте и проверка ответа. Добавили
  поле — всё три появились сами и разъехаться не могут.
- **Мастер настройки** (`agent/interview.py`): семь с лишним вопросов при первом
  обращении нового пользователя, `--настроить` в консоли и форма в вебе. Мастер
  не читает ввод сам — отдаёт вопросы и принимает ответы, поэтому одинаково
  работает в консоли, в вебе и в тесте.
- **Четыре заготовки профиля**: инженер, тимлид, новичок, менеджер.
  `--заготовка тимлид` или кнопка на странице. Пользователь с именем заготовки
  получает её автоматически: `--кто менеджер`.
- **Проверка соблюдения профиля** (`PreferenceChecker`): длина в словах (код в
  счёт не идёт), наличие блоков ```, обращение на «ты» или «вы», упоминание
  имени, язык ответа. Расхождение — повтор с напоминанием.
- **Сценарии** (`agent/scenarios.py`, `long/<кто>/scenarios.json`): «на такой
  запрос зови таких-то агентов в таком порядке». Каждый шаг — отдельный вызов со
  своей ролью, своей моделью из каталога и своей стадией задачи; результат
  ложится в рабочую память и становится входом следующего шага. Три готовых
  сценария: «напиши фичу» (5 шагов), «разбери legacy» (3), «оцени задачу» (2).
- **Проверка сценария до исполнения**: имена шагов не повторяются, роли и стадии
  существуют, маршрут проходит по разрешённым переходам конечного автомата.
  Сценарий, который сломался бы на середине, отваливается до первого вызова
  модели, а не после того, как потратил токены.
- **Роль модели `фронтенд`** (`groq-qwen27b`) — для шага сценария, который пишет
  обвязку карты на OpenLayers.
- **`compare.py --профили`** — один вопрос через все заготовки с механическими
  признаками ответа, и **`--сценарий ИМЯ`** — прогон сценария по шагам.
- **Переключение пользователя в вебе** и правка профиля прямо на странице:
  изменил предпочтение — следующий ответ собирается уже по-новому.

### Изменено

- **Настройки пользователя идут в промпт на всех четырёх стадиях задачи.** В Дне
  11 на стадии проверки стиль из промпта убирался: он не влияет на поиск
  дефектов. Теперь ответ сверяется с профилем кодом, и стадия, где профиль не
  показали, гарантированно дала бы расхождение и лишний повтор.
- **Блок «профиль» разделён надвое**: «настройки пользователя» (что он задал про
  себя) и «рамки проекта» (ограничения и контекст). В трейсе видно порознь,
  какая часть на что повлияла.
- **Собранные результаты шагов обрезаются при сборке промпта.** Рабочая память
  хранит результат целиком — он должен пережить перезапуск, — а в промпт пять
  шагов сценария целиком не поместятся.
- **Маршрутизатор знает про новые разделы профиля**: «обращайся ко мне на ты»
  теперь попадает в `обращение`, а не в случайный ключ.

### Исправлено по ходу разработки

- **Предпочтения применялись к каждому шагу сценария.** Промежуточный шаг пишет
  для следующего агента, а не для человека, и «Привет, Максим» в ответе
  аналитика — это потраченные токены и укороченный вход для архитектора. Теперь
  настройки применяются только к последнему шагу; остальные собираются с
  `personal=False`, и в трейсе видно, почему блок пропущен.
- **Косметическое расхождение с профилем поднимало модель до платной.** Лестница
  эскалации срабатывала на любом повторе, и ответ, который был на двадцать слов
  длиннее просимого, уходил на `ds-pro`. Теперь эскалация — только из-за
  нарушения инварианта; расхождение с профилем повторяется на той же модели.
- **Маршрутизатор не поднимался на ступень при пустом ответе модели.** Эскалация
  срабатывала только на неразбираемом JSON, хотя пустой ответ от слабой модели —
  самая частая из неудач. Теперь оба случая ведут к смене модели.
- **Новый пользователь получал чужой профиль.** Начальное наполнение задавало
  предпочтения инженера всем подряд, и мастер настройки не срабатывал ни разу.
  Теперь предпочтения достаются только пользователю, названному как заготовка;
  остальные начинают с умолчаний и с предложением настроить.
- **В промпт уходило противоречие** «кода не показывай» и «примеры на Python»
  одновременно. Язык примеров молчит, когда код не нужен.
- **Результаты шагов сценария уходили в промпт дважды** — как явный вход шага и
  ещё раз в блоке «собранные данные» рабочей памяти. Из-за этого пятый шаг из
  пяти перестал помещаться в минутный лимит Groq, и прогон падал после того, как
  четыре предыдущих уже потратили токены. Теперь шагу сценария рабочая память не
  показывается: что ему видеть, решает сценарий. Прогон подешевел на 13%.
- **Каталог моделей устарел молча.** `qwen/qwen3.6-27b`, перенесённая из Дня 10,
  у Groq больше не существует — её сменила `qwen/qwen3.8-27b`, и выяснилось это
  посреди сценария. Добавлена команда `--проверить`, которая спрашивает у
  провайдеров, отвечают ли модели каталога. Первая версия проверки сверялась со
  списком `/models` и объявила несуществующими `glm-4.5-flash` и
  `deepseek-v4-flash` — обе отвечают, просто в перечне их нет; проверка заменена
  на настоящий запрос в один токен.
- **Напоминание о длине было расплывчатым.** На «сократи до 180 слов» ответ
  возвращался на 254 словах. Указание с числами — «в ответе 254 слова вместо
  180, убери не меньше 74» — дало 190 слов.
- **Запрос в проверке сценария не соответствовал сценарию**: «напиши фичу»
  прогонялся на тексте, начинавшемся со слов «оцени задачу». У каждого сценария
  теперь свой запрос.
