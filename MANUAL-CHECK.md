# Ручная проверка Дня 17 в браузере

Сценарий для проверки руками: у агента есть свой MCP-сервер вокруг API трекера
задач, модель сама решает вызвать инструмент, агент исполняет вызов и отвечает
по полученным данным, а всё, что меняет данные в трекере, ждёт вашего
подтверждения.

Каждый шаг устроен одинаково: **что сделать** → **что должно получиться**.

Время: около 30 минут. Вызовов модели: 4–6. В шапке выберите модель
**DeepSeek V4 Flash (ds-flash)**: она отвечает быстро и уверенно пользуется
инструментами.

Сценарий пройден в браузере (headless Chrome, порт 5001) на живом моке трекера
и живой модели: ожидания ниже — то, что происходит на самом деле.

---

Этот файл — для человека. Если нужно **показать** день, а не проверить, есть
отдельный сценарий: [DEMO-CHROME.md](DEMO-CHROME.md) — шесть сцен с готовым
промптом для браузерного расширения Claude in Chrome, стенд одной командой
(`bash demo_stand.sh`) и запись окна браузера (`bash record_demo.sh`). Тот же
сценарий проходит и скрипт-водитель, если расширение не подключилось:
`bash demo_show.sh`.

## Часть 0. Подготовка

```bash
cd ~/Документы/AI-Advent-Challenge/Day-17
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt     # Flask, httpx и MCP SDK (mcp 2.x)
cp -n .env.example .env                       # если .env ещё нет
mv memory memory-до-проверки 2>/dev/null || true
.venv/bin/python web.py
```

**Во втором терминале поднимите мок-трекер** — это то самое API, вокруг которого
построен инструмент дня. Без него инструменты подключатся, но вызовы будут
отвечать «Трекер не отвечает по адресу…»:

```bash
cd ~/Документы/AI-Advent-Challenge/Day-17
.venv/bin/python tracker_api.py --сброс       # 127.0.0.1:8766, данные заново
```

Восемь задач очереди `MIG` («Перенос ГИС газовых сетей») и две задачи `SUP`
(поддержка legacy) — их и будет читать агент.

Системный `python3` не подойдёт: в нём нет ни Flask, ни MCP SDK. Для серверов
`filesystem` и `everything` нужен Node.js 18+ (`node --version`).

**Первый запуск `npx` скачивает пакет, и это может занять минуты.** Чтобы не
ждать посреди проверки, прогрейте кэш заранее во втором терминале:

```bash
npx -y @modelcontextprotocol/server-everything --help < /dev/null
npx -y @modelcontextprotocol/server-filesystem /tmp < /dev/null
# второй не завершится сам: Ctrl+C, когда появится «Secure MCP Filesystem Server running on stdio»
```

Откройте <http://127.0.0.1:5000>.

- [ ] Заголовок вкладки — «Агент миграции ГИС — подключение MCP», на странице —
      «Агент миграции ГИС — внешние инструменты по MCP».
- [ ] Вступление начинается с абзаца про панель **MCP**.
- [ ] Справа **первой** стоит карточка **«MCP-серверы»** со счётчиком **5**.

## Часть 1. Инструмент зарегистрирован и виден

**1.1.** В панели **MCP-серверы** справа найдите `tracker` и нажмите
**Подключиться**.

- [ ] Карточка стала зелёной: «tracker 17.0 («Трекер задач миграции»)»,
      протокол и способ рукопожатия, «Инструменты: 5».
- [ ] Раскройте список инструментов. Три помечены **только чтение**
      (`list_queues`, `list_issues`, `get_issue`), два — **меняет данные**
      (`add_comment`, `move_issue`).
- [ ] У `get_issue` видны параметры: `key*` (звёздочка — обязательный) с
      пояснением «Ключ задачи в трекере, например «MIG-2»» и `comments`.
- [ ] В строке инструментов — цена: «схема ≈ 1 278 ток. в каждом запросе».

**1.2.** Раскройте «JSON-схема входа» у `list_issues`.

- [ ] Видны `"properties"` со всеми пятью параметрами, а у `limit` —
      `"minimum": 1` и `"maximum": 50`. Это то, что уходит модели.

**1.3.** Нажмите **Подключиться** у сервера `tracker-real`.

- [ ] Если в `.env` заданы `TRACKER_TOKEN` и `TRACKER_ORG` — карточка зелёная,
      и инструментов **три**: у настоящего Трекера меняющие не регистрируются,
      пока не задано `TRACKER_WRITE=1`. Это тот же сервер, только адрес другой.
- [ ] Если токена нет — карточка пунктирная: «не хватает переменных
      TRACKER_TOKEN, TRACKER_ORG». К нему даже не подключались.

## Часть 2. Вызов инструмента руками

**2.1.** В карточке `tracker` у инструмента `list_issues` нажмите **Вызвать** и
в окне аргументов введите `{"status": "inProgress"}`.

- [ ] В переписке появилась строка «↳ tracker__list_issues({...}) — 0,1 с» и под
      ней тёмный блок с ответом: задачи `MIG-2`, `MIG-3`, `SUP-11` с темами,
      статусами и сроками.
- [ ] Подтверждения никто не спросил: вызов затеяли вы, а не модель.

**2.2.** Нажмите **Вызвать** у `get_issue` и введите `{"key": "MIG-999"}`.

- [ ] Строка вызова красная, в ней причина от самого API: «В трекере нет такого
      объекта (404)». Страница не сломалась.

## Часть 3. Модель сама зовёт инструмент

**3.1.** Под полем ввода включите **Давать инструменты модели**. Рядом поле
серверов — оставьте `tracker`.

- [ ] Справа от переключателя появилось: «5 инстр. (2 меняющих), схема ≈ 1 278
      ток. в каждом запросе».

**3.2.** Спросите: «Посмотри в трекере: какие задачи переноса сейчас в работе и
что горит по срокам?»

- [ ] Под ответом — строки вызовов «↳ tracker__list_issues(...)», обычно
      два-шесть вызовов: модель сначала смотрит список, потом открывает
      отдельные задачи.
- [ ] В самом ответе — ключи задач (`MIG-2`, `MIG-3`, `MIG-5`), их темы, сроки
      и исполнители. Этих данных нет ни в памяти агента, ни в промпте: они
      пришли из трекера.
- [ ] Строка расхода: вход заметно больше обычного — это и есть цена схемы плюс
      ответы инструментов.

**3.3.** Задайте вопрос, для которого трекер не нужен: «Чем векторные тайлы
лучше картинок MapServer? Коротко.»

- [ ] Ответ пришёл **без** строк «↳»: инструменты даны, но модель сама решила,
      что звать нечего.

## Часть 4. Изменение — только с подтверждения

**4.1.** Попросите: «Добавь к задаче MIG-7 в трекере комментарий: «Проверено
вручную»».

- [ ] Строки «↳ tracker__add_comment» в переписке **нет**: вызов не выполнялся.
- [ ] Справа появилась карточка **Заявки на изменение** с одной заявкой:
      инструмент `tracker__add_comment`, аргументы `key: MIG-7` и текст
      комментария, строка «из-за вопроса: …».
- [ ] В ответе агент говорит, что подготовил комментарий и просит подтвердить.

**4.2.** Нажмите **Подтвердить и выполнить**.

- [ ] В переписке: «✓ Заявка №1 исполнена: tracker__add_comment» и тёмный блок
      с ответом инструмента, где `"добавлен": true`.
- [ ] Карточка заявок исчезла — ждущих больше нет.

**4.3.** Проверьте, что изменение дошло до трекера: в панели MCP у `get_issue`
нажмите **Вызвать** и введите `{"key": "MIG-7", "comments": 5}`.

- [ ] В ответе среди комментариев есть «Проверено вручную» с автором и датой.

**4.4.** Попросите ещё раз, но теперь откажите: «Переведи MIG-4 в статус
closed». Когда появится заявка, нажмите **Отклонить** и впишите причину.

- [ ] В переписке: «Заявка №2 отклонена — вызов не делался.»
- [ ] Проверьте `get_issue` с `{"key": "MIG-4"}` — статус не изменился.

## Часть 7. Прошлые дни не сломаны

MCP стоит рядом с агентом и его не трогает. Короткий проход по наследству:

**7.1. Ответ с разбором (Дни 11–12).** Спросите: «Какой ORM использовать для
геометрии в новой системе?»

- [ ] Ответ пришёл, под ним «Что ушло в промпт» с блоками слоёв памяти.

**7.2. Инвариант (День 14).** Спросите: «Перепиши сервис на Laravel».

- [ ] Красный отказ: «Не могу этого предложить: это нарушило бы инварианты
      проекта», правило `стек-бэкенд`, «Почему так решено», «Что именно не
      проходит: «laravel» в запросе», «Что можно вместо».
- [ ] Последняя строка отказа: «Запрос отклонён до обращения к модели, поэтому
      токены не потрачены», и системная строка «Модель не вызывалась — отказ по
      инварианту».

- [ ] Отказ приходит сразу, за доли секунды. Проверка запроса — код, и с
      Дня 16 она идёт раньше маршрутизатора реплик: не зовутся ни отвечающая
      модель, ни дешёвая модель маршрутизатора.

**7.3. Подключение MCP (День 16).** Нажмите **Подключиться ко всем** в панели
MCP.

- [ ] Карточки всех серверов на месте: свои (`tracker`, `tracker-real`,
      `agent-state`), эталонные через npx, удалённые. У `filesystem` видны
      закрытые фильтром инструменты.

**7.4. Переходы (День 15).** В карточке «Задача» заведите задачу
`проверка-мсп`, нажмите **🔒 готово**.

- [ ] В чате разбор отказа: «в жизненном цикле нет такого перехода» и законный
      маршрут планирование → исполнение → проверка → готово.

**7.5. Пауза (День 13).** Включите «подтверждать смену стадии» и спросите:
«оцени задачу: перенести справочник организаций». Запустится сценарий оценки
из двух шагов (декомпозиция → оценщик).

- [ ] Задача встаёт на паузе. Чаще всего первый шаг просит сведений: «на паузе:
      не хватает сведений», ожидание «ответ-пользователя» с вопросом шага. Если
      вопросов нет — «на паузе: переход между стадиями».
- [ ] «Продолжить» сдвигает задачу: в прогоне она дошла до «на паузе: переход
      между стадиями» с вопросом «перейти со стадии «planning» на «execution» и
      запустить шаг «оценщик»?».

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| `ModuleNotFoundError: No module named 'flask'` или `'mcp'` | запущен системный `python3` — запускайте `.venv/bin/python web.py` |
| «Трекер не отвечает по адресу http://127.0.0.1:8766» | не поднят мок: `.venv/bin/python tracker_api.py` во втором терминале |
| «Трекер не принял токен (401)» у `tracker` | мок запущен со своим `--токен`; верните значение по умолчанию или задайте `TRACKER_MOCK_TOKEN` в `.env` |
| `tracker-real`: «Трекер отказал в доступе (403)» | организация заведена в Яндекс 360 — поставьте `TRACKER_ORG_HEADER=X-Org-ID` в `.env` |
| `tracker-real` не показывает `add_comment` | так и задумано: у настоящего Трекера запись включается `TRACKER_WRITE=1` |
| модель зовёт инструменты, но отвечает «данных нет» | посмотрите строки «↳»: красная означает ошибку API, её текст модель видела |
| карточки MCP нет, есть красная «Файл … — не JSON» | в `mcp-servers.json` синтаксическая ошибка — `git checkout mcp-servers.json` |
| `filesystem` / `everything`: «не найдена команда «npx»» | нет Node.js: <https://nodejs.org>, нужна версия 18+ |
| `filesystem` / `everything`: «не ответил за 120 с» | первый запуск npx качает пакет — прогрейте кэш (часть 0) и повторите |
| `deepwiki`: «нет соединения с mcp.deepwiki.com» | нет интернета или сайт недоступен; остальные серверы от этого не зависят |
| `github`: «в заголовках запроса есть не-латинские символы» | в `GITHUB_TOKEN` попала кириллица — токен пишется латиницей |
| `github` не готов, хотя токен вписан | строка в `.env` должна быть `GITHUB_TOKEN=значение` без пробелов вокруг `=` |

После проверки можно вернуть прежнюю память:

```bash
rm -rf memory && mv memory-до-проверки memory
```
