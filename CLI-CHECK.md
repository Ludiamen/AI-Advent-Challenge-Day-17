# Проверка Дня 17 через консоль

То же, что `MANUAL-CHECK.md`, но без браузера. Проверяются три пласта:

* **новое в Дне 17** — свой MCP-сервер вокруг API трекера задач: инструменты
  зарегистрированы и описаны, агент вызывает их руками и по решению модели,
  результат попадает в ответ, а меняющий вызов исполняется только после
  подтверждения заявки;
* **наследство Дня 16** — подключение MCP как таковое: список серверов,
  соединение по stdio и HTTP, фильтр, понятные сбои;
* **наследство Дней 11–15** — слои памяти и разбор промпта, заготовки профиля,
  пауза, инварианты с отказом за ноль токенов, ворота переходов и диалоговый
  режим.

Мок-трекер поднимает сам скрипт прогона — на свободном порту и со своими
данными в `cli-check-memory/tracker-data.json`. Руками его запускать не нужно.

```bash
cd ~/Документы/AI-Advent-Challenge/Day-17
.venv/bin/python check_cli.py                # весь чек-лист + отчёт в CLI-CHECK-RESULTS.md
.venv/bin/python check_cli.py --без-модели   # без живых вызовов модели
.venv/bin/python check_cli.py --в отчёт.md
```

Ниже вместо `.venv/bin/python` написано просто `python`: так короче, а с
активированным окружением (`source .venv/bin/activate`) это одно и то же.
Команды с `$ФАЙЛ` подразумевают файл серверов прогона
(`cli-check-memory/mcp-configs/tracker.json`); вручную то же самое делается с
`mcp-servers.json`, если в соседнем терминале поднят `python tracker_api.py`.

## Часть 1. Свой инструмент MCP

**1.1. Инструменты зарегистрированы**

```bash
python cli.py --mcp tracker
```

- [ ] «Соединение: установлено», «Сервер: tracker 17.0 («Трекер задач
      миграции»)».
- [ ] Пять инструментов: `list_queues`, `list_issues`, `get_issue` —
      `[только чтение]`; `add_comment`, `move_issue` — `[меняет данные]`.
- [ ] У `get_issue` параметры `key* (string) — Ключ задачи в трекере, например
      «MIG-2»` и `comments (integer)`.
- [ ] «схема ≈ 1 278 ток. в каждом запросе».

**1.2. Входные параметры описаны схемой**

```bash
python cli.py --mcp tracker --mcp-схема
```

- [ ] У `get_issue` в схеме `"required": ["key"]`, у `list_issues` —
      `"maximum": 50` для `limit`. Это то, по чему модель выбирает значения.

**1.3. Без права записи меняющих инструментов нет**

```bash
python cli.py --mcp tracker-real          # или tracker-readonly в файле прогона
```

- [ ] «Инструменты: 3». `add_comment` и `move_issue` в списке нет: у настоящего
      Трекера запись включается только `TRACKER_WRITE=1`.
- [ ] Если `TRACKER_TOKEN` в `.env` не задан — сервер помечен «не хватает
      переменных TRACKER_TOKEN, TRACKER_ORG» и пропущен.

**1.4. Что досталось модели**

```bash
python cli.py --инструменты tracker
```

- [ ] Имена в том виде, в каком их видит модель: `tracker__list_issues` и так
      далее.
- [ ] У меняющих — пометка «меняет данные; подтверждение человека».
- [ ] Итог: «Серверов подключено 1 из 1. Инструментов 5 (3 читающих,
      2 меняющих); их схема ≈ 1 278 ток. в каждом запросе».

**1.5. Вызов руками**

```bash
python cli.py --вызвать tracker__list_issues --аргументы '{"status": "inProgress", "limit": 5}'
```

- [ ] Заголовок «tracker__list_issues(status=inProgress, limit=5) — ок, 0,2 с»
      и JSON с задачами `MIG-2`, `MIG-3`, `SUP-11`.
- [ ] Подтверждения не спрашивают: вызов затеял человек.

**1.6. Ошибка инструмента названа**

```bash
python cli.py --вызвать tracker__get_issue --аргументы '{"key": "MIG-999"}'
```

- [ ] «ОШИБКА» и причина от самого API: «В трекере нет такого объекта (404)».
- [ ] Код возврата 1.

**1.7. Выдуманный ключ не уходит в API**

```bash
python cli.py --вызвать tracker__get_issue --аргументы '{"key": "../../etc/passwd"}'
```

- [ ] «не похоже на ключ задачи. Ключ пишется латиницей: очередь, дефис,
      номер — например «MIG-2»». Запроса к трекеру не было.

**1.8. Заявок пока нет**

```bash
python cli.py --заявки
```

- [ ] «Ждущих заявок нет» и пояснение, откуда они берутся.

## Часть 2. Доказательный прогон

```bash
python check_tools.py --без-модели     # части 1–3, 6, 7 без единого вызова модели
python check_tools.py                  # плюс живые части 4 и 5
```

- [ ] Часть 1: «список совпадает с объявленным в tracker_server.py», пометки
      читающих и меняющих, «без TRACKER_WRITE=1 меняющих инструментов в списке
      нет (3 вместо 5)».
- [ ] Часть 2: у каждого инструмента «схема JSON Schema корректна, … все с
      описанием»; `limit=99` отклонён схемой; `../../etc/passwd` отклонён кодом.
- [ ] Часть 3: «совпали с прямым запросом к API», «счётчик найденного взят из
      заголовка API X-Total-Count», «служебных полей API в выжимке нет», «на
      списке из 8 задач выжимка короче ответа API … на 65% меньше».
- [ ] Часть 4 (живая): «модель сама позвала инструменты», «в ответе есть данные
      из трекера, которых не было в промпте».
- [ ] Часть 5 (живая): «меняющий вызов НЕ выполнен сразу», «появилась заявка»,
      «комментарий появился в самом API», «отклонённая заявка не меняет ничего».
- [ ] Итог: «провалов 0».

Часть 3 — главный довод дня. Результат инструмента сверяется не с ожиданием в
тесте, а с ответом самого API, запрошенным отдельно, мимо MCP.

## Часть 6. Живые вызовы модели

```bash
python cli.py --инструменты tracker "Посмотри в трекере: какие задачи переноса в работе?"
python cli.py --инструменты tracker "Добавь к задаче MIG-7 комментарий: «Проверено»."
python cli.py --заявки
python cli.py --подтвердить 1
python cli.py --вызвать tracker__get_issue --аргументы '{"key": "MIG-7", "comments": 5}'
python cli.py --подтвердить 1
```

- [ ] Первая команда: строки «↳ tracker__list_issues(...)» и ответ с ключами
      задач из трекера.
- [ ] Вторая: строки вызова **нет**, зато «! Заявка №1 tracker__add_comment(…)»
      и подсказка «Исполнить: --подтвердить 1 · отклонить: --отклонить 1».
- [ ] `--заявки` показывает ту же заявку — её завёл другой процесс.
- [ ] `--подтвердить 1`: «Заявка №1 исполнена», в ответе инструмента
      `"добавлен": true`.
- [ ] `get_issue` показывает комментарий «Проверено» — изменение дошло до API.
- [ ] Повторное `--подтвердить 1`: «Заявка №1 уже выполнена», код 1.
